Toll Gate

A policy gateway between AI agents and PayPal. Agents authenticate with API keys and ask permission to move money. The gateway decides — allow, deny, require human approval, or deduplicate — enforces spending caps atomically, audits everything, and holds the PayPal credentials so agents never touch money directly.

FastAPI gateway MCP server for agents LangGraph + Gemini dispute agent PostgreSQL + Redis state 285 tests against real databases MIT licensed

The problem

Autonomous agents are good at deciding what to do and bad at being trusted with doing it. Give an LLM a PayPal credential and a refund endpoint, and one hallucinated justification moves real money. Toll Gate separates the two roles:

The agent proposes.

It authenticates with its own key, states an action, an amount, and an idempotency key. That is a request, not a capability — it cannot execute anything itself.

The gateway disposes.

A policy engine checks the agent's allowlist, per-transaction cap, rolling 24-hour cap, and approval threshold — under a row lock, in one transaction — and only then (maybe) calls PayPal.

What is in the box

  • Policy engine — agent identity, per-agent policies, atomic spending caps, an approval state machine, and an append-only audit log.
  • PayPal client — OAuth2 with cached tokens, orders, captures, refunds, disputes; deterministic PayPal-Request-Id idempotency so retries can never double-refund.
  • MCP server — the same gateway exposed to agents as Model Context Protocol tools over streamable HTTP at /mcp. Money-moving tools run the full policy engine first.
  • Dispute agent — an autonomous LangGraph agent that gathers evidence, drafts a response, fact-checks itself with a critic, and proposes a schema-validated refund. It talks to the gateway only through MCP, like any other agent.
  • Webhook pipeline + outbox worker — PayPal dispute webhooks are verified, persisted, and enqueued in one transaction; a worker claims jobs and runs (or resumes) the agent, with retries, backoff, and a dead-letter queue.
  • Admin dashboard — a static, offline-capable single-page app at /dashboard/: live approvals with the agent's reasoning and cited evidence, one-click approve/reject, actions, audit feed, metrics, and dead letters. Nothing is ever truncated.
About this site. These docs are one self-contained HTML file — no JavaScript, no CDN, no API calls. They stay up and accurate regardless of whether any Toll Gate service is running. The live links in the sidebar are just links; everything you need to understand and run the system is on this page.

How it works

Every request gets a verdict

An agent posts an action (today: refund, create_order) with an amount and an idempotency key. The engine returns exactly one of four outcomes — always HTTP 200, because a denial is a successful answer, not an error:

OutcomeMeaningMoney
allowedWithin policy. The gateway executes the call on PayPal.Moves now
pending_approvalAmount ≥ the agent's approval threshold. An approval row is created and waits for a human.Reserved, not moved
deniedAction not in the agent's allowlist, or a cap is exceeded.Never
deduplicatedThe idempotency key was already used by this agent. The original verdict is replayed.Never twice

Caps are atomic, even under concurrency

The engine takes SELECT … FOR UPDATE on the agent row first: concurrent requests from one agent serialize, while different agents never block each other. The rolling 24-hour cap counts committed allowed actions plus live pending_approval ones — a pending approval reserves headroom; rejecting or expiring it releases the headroom. A partial unique index on (agent_id, idempotency_key) makes double-spending the same key physically impossible at the database level. This is not a claim, it is a test: 50 barrier-aligned threads race $10 actions against a $100 cap, and exactly ten win — total exactly $100.00.

Approvals are a state machine with a human in the loop

pending → approved → executed, with rejected, expired, and failed as exits. CHECK constraints enforce timeline consistency; illegal transitions return 409. Executing an approved refund carries a deterministic PayPal-Request-Id derived from the action id, so even a replayed execution cannot refund twice.

Every decision is written down, in one transaction

A decision writes four rows atomically — the action, an audit entry, an immutable domain event, and an outbox row for relays. All land or none do. The audit log is append-only and records auth failures too, so an attacker probing keys leaves the same kind of trail as an agent working normally.

Architecture

One FastAPI process serves every doorway: REST for agents, MCP for tool-calling agents, a signature-verified webhook door for PayPal, and the static dashboard for operators. On Render's free plan the outbox worker runs as a thread inside the same process (see Deployment); everywhere else it is a separate python -m worker process. The agent's checkpoints and run telemetry live in their own database, so the gateway schema never grows foreign keys into data another process owns.

One FastAPI process serves every door. On Render's free plan the outbox worker runs in-process (a daemon thread); everywhere else it is a separate python -m worker process.

Trust boundaries

  • Agents never hold PayPal credentials. The gateway owns them; agents own a revocable tg_… key with a policy attached.
  • The dispute agent never touches the gateway's database. Its only doorway is MCP, so its refunds pass the same caps and audit as anyone else's.
  • The worker never holds PayPal credentials either. Its single secret is the queue database URL; its agent identity is a regular key.
  • The admin key is a deployment secret (environment variable), never an agent key — agents cannot provision or approve as admins.
  • Webhook identity is the signature. In production only PayPal's own verification API can admit an event; unverifiable deliveries are rejected (PayPal retries).

The dispute agent

An autonomous LangGraph agent that handles a PayPal dispute end to end: gather evidence through MCP reads, have Gemini draft a response, fact-check the draft with a critic, emit a schema-validated refund decision, and request the refund through the gateway. If the gateway demands human approval, the graph pauses durably — the state is checkpointed in PostgreSQL and the process can die; a fresh process resumes by thread id after the decision.

The graph only moves forward. Every failure branch is terminal, and only a human approval can wake execute_refund.

Anti-hallucination guards

  • One-pass critic, no revision loop. Every 17-character-ID-shaped and timestamp-shaped token in the draft must appear verbatim in the evidence JSON (a deterministic scan), and an LLM fact-check verdict must say supported — unparseable verdicts fail closed. A rejected draft ends the run; it is never sent back for rewording, so a hallucination cannot be laundered by a rewrite.
  • The decision is a schema, not prose. RefundDecision forbids extra fields, enforces the gateway's ID and timestamp formats, requires cited transaction IDs to exist in the evidence, caps the refund at the transaction amount, and forces escalate_human when confidence is below the floor (default 0.6).
  • Money never trusts the prose. Whatever the reasoning says, execution passes the policy engine, caps, and — above the threshold — a human. The reasoning exists so the human can ask "is this real?" before approving.

Budgets, retries, telemetry

Each run gets a RunMeter: a unique run id, a hard token budget checked before every call, and USD cost from a static price table. Transient Gemini failures (429, 5xx, network) retry with exponential backoff plus jitter; 4xx errors never retry. Every run upserts an agent_runs row — status, tokens in/out, cost, LLM calls, confidence, proposed action — which doubles as the calibration dataset for the confidence floor. When a run pauses for approval, a provisional row is written immediately carrying the full decision (reasoning and cited evidence), so the dashboard can show what the agent was thinking while it waits.

Webhook pipeline & outbox worker

PayPal dispute webhooks arrive at POST /webhooks/paypal. The endpoint's contract: answer 200 fast, and never do work inline that can be done later. Verification, persistence, and job enqueue happen in one transaction; running the agent is the worker's job.

Webhook → queue → agent → pause → human → resume → refund, with every arrow crash-safe.

The guarantees, one by one

  • Fail-closed verification. Production deliveries are checked against PayPal's verify-webhook-signature API using the raw bytes; if the verifier is unreachable the delivery is rejected (502) — an unverifiable event is not an accepted event. A dev HMAC strategy exists for the simulator and fails closed when unconfigured.
  • At-least-once dispatch is safe. The run id equals the checkpoint thread id equals webhook-{dispute_id}. A redelivered job finds the finished thread and no-ops.
  • Claims never block work. The claim is a short SKIP LOCKED transaction; handlers run outside it, so a slow LLM call holds no row locks.
  • Classification defaults to retryable. Only explicitly permanent errors (bad evidence, schema failure, critic rejection, budget exhaustion, and the resume rails) dead-letter immediately; anything ambiguous retries with backoff.
  • Crashed workers don't strand jobs. A lease sweep reclaims processing rows whose claim is older than the lease, or dead-letters them if attempts are spent.
  • Deciding an approval and waking the agent are atomic. The admin decision endpoint writes the decision and enqueues the resume job in the same transaction — a decision can never be recorded without the agent being eventually resumed.
  • Money moves once. Resume rails verify the run exists, is paused, and matches the approval; a redelivered resume records the outcome without re-executing; the refund itself rides the gateway's deterministic request id.

Admin dashboard

A static single-page app served by the gateway at /dashboard/, built on AG Grid Community — vendored, not CDN-loaded (fonts included as data URIs), so the page itself never reaches the network for anything but its JSON APIs. First load prompts for the admin key, stored in localStorage and sent as X-Admin-Key; a 401 re-prompts.

Panels

  • Approvals (full width, top) — pending approvals joined with the paused agent run: confidence, the full reasoning text, and every piece of cited evidence. One-click Approve/Reject opens a confirm dialog that names the amount and warns that approving executes a real refund; the operator identity is asked once and remembered.
  • Actions and Audit — side by side, filterable, with full detail JSON.
  • Dead letter — failed jobs with their complete error text, stack traces included.
  • Metrics — counters, money totals, median decision latency, agent-run status mix.

All panels poll every two seconds (ticks never overlap) and diff by row id, so live updates don't flicker or reset your scroll position.

The no-truncation contract

Nothing is ever cut off. Every column wraps (wrapText + autoHeight); cells force pre-wrap and overflow-wrap: anywhere, so a 1,300-character reasoning paragraph, a multiline stack trace, a 240-character unbroken token, and a 1.8 KB JSON blob all wrap inside the cell — the row grows instead. The word "ellipsis" is banned from the HTML, CSS, and JS by a test, and cell text is pinned selectable/copyable (enableCellTextSelection required, suppressCellFocus banned). Timestamps render on two lines. A contract test fails the build if any of this regresses.

Graceful degradation

The dashboard APIs join two databases (gateway rows + agent reasoning) in application code. If the agent database is unreachable, approval rows degrade to agent: null and the page shows a banner — the approvals list itself never fails because a secondary store is down.

Getting started

Prerequisites

  • Python ≥ 3.12 and uv
  • Docker (PostgreSQL 16 + Redis 7) for local state
  • PayPal sandbox credentials from developer.paypal.com
  • A Gemini API key for the dispute agent

1 · Infrastructure

docker run -d --name tollgate-pg -e POSTGRES_USER=tollgate -e POSTGRES_PASSWORD=tollgate \
  -e POSTGRES_DB=tollgate -p 5433:5432 postgres:16-alpine
docker run -d --name tollgate-redis -p 6380:6379 redis:7-alpine

Ports 5433/6380 avoid the native services that often own 5432/6379 on dev machines. The agent's own database is created and migrated automatically on first use.

2 · Application

git clone https://github.com/RajNair06/tollgate.git
cd tollgate
uv sync
cp .env.example .env    # fill PayPal creds; ADMIN_API_KEY: tga_$(openssl rand -hex 24)
uv run alembic upgrade head
uv run uvicorn main:app --port 8000     # terminal 1: gateway + MCP + webhooks + dashboard
uv run python -m worker                 # terminal 2: outbox worker

3 · Provision an agent

curl -s -X POST localhost:8000/v1/admin/agents \
  -H "X-Admin-Key: $ADMIN_API_KEY" -H 'Content-Type: application/json' \
  -d '{"name":"refund-bot","allowed_actions":["refund"],
       "per_txn_cap":"25.00","rolling_24h_cap":"100.00","approval_threshold":"20.00"}'
# → {"agent_id":1,"api_key":"tg_...","key_id":1,...}   (the key is shown ONCE)

4 · Ask for a decision

curl -s -X POST localhost:8000/v1/agent-actions \
  -H "X-API-Key: tg_..." -H 'Content-Type: application/json' \
  -d '{"action_type":"refund","amount":"22.00","idempotency_key":"req-0001"}'
# → {"outcome":"pending_approval","reason_code":"APPROVAL_REQUIRED","approval_id":1,...}
# replaying the same idempotency_key → {"outcome":"deduplicated",...}

Amounts are decimal strings — JSON numbers are rejected. All four verdicts return HTTP 200; 4xx always means the request failed.

5 · Try the webhook pipeline

# fires a signed dispute event at the real endpoint (dev HMAC strategy)
WEBHOOK_SHARED_SECRET=dev-shared-secret uv run python scripts/simulate_dispute.py

The simulated dispute does not exist in the sandbox, so the dispatched run fails fast with a real RESOURCE_NOT_FOUND and lands in the dead-letter panel — the failure path, demonstrated live.

6 · Demo the full approve → resume → refund loop

The sandbox cannot generate real disputes, so a seeder script bridges the gap: create a real pending approval (step 4 against a real sandbox capture), then

uv run python scripts/demo_paused_run.py --approval-id 6 --action-id 70 \
    --dispute-id PP-D-90002

This runs the real graph, checkpointer, and runner against a scripted world. Its reasoning text is hand-written fixture prose and says so: it opens with "[DEMO FIXTURE — synthetic text, not model output]". Open the dashboard, click Approve, and the worker resumes the checkpoint and executes a real sandbox refund.

7 · Open the dashboard

http://localhost:8000/dashboard/ — paste your ADMIN_API_KEY at the prompt.

Run the tests

uv run pytest        # 285 tests, ~6 min — needs the Docker containers

Tests run against real PostgreSQL (serialization, unique indexes, CHECK constraints, checkpointing, queue mechanics are database behavior, so mocks would prove nothing). The PayPal client is tested offline via mock transport; the MCP server is tested end-to-end over real streamable HTTP.

Deployment

The reference deployment runs entirely on free tiers:

PieceHostNotes
Gateway (+ MCP, webhooks, dashboard, root card)Render free web serviceSingle instance; sleeps after ~15 min idle, cold start ~50 s
Outbox workerIn-process thread (WORKER_IN_PROCESS=1)Render's free plan cannot run background workers — see the honest note below
PostgreSQL (gateway + agent data)Supabase freeSession-mode pooler; the agent tables share the postgres database because poolers cannot CREATE DATABASE
RedisRender Key Value (free)Rate limits + PayPal token cache
These docsGitHub PagesStatic, independent of everything above
The in-process worker is a free-plan accommodation, not the recommended shape. The design intent is a separate python -m worker process (crash isolation, independent scaling, no shared fate with the web tier). Render's free plan forbids background workers, so to stay at $0 the deployment embeds the identical worker stack as a daemon thread inside the web process. Consequences: when the free service sleeps, the worker sleeps with it — queued jobs wait for the next wake-up (webhook deliveries and dashboard traffic wake it; PayPal retries until accepted). Correctness is unaffected — claims use SKIP LOCKED, crashed leases are swept, dispatch is idempotent — only latency degrades. Keep exactly one replica. Moving to a paid worker later is an env-var change, not a code change.

Other free-tier caveats, stated plainly

  • Supabase free projects pause after ~1 week of inactivity; wake them from the Supabase dashboard.
  • The Supabase pooler is in Sydney while Render free runs in Oregon — every query crosses the Pacific (~150–180 ms), so multi-round-trip requests take about a second. Fine for a demo; fix later by co-locating regions.
  • Credentials live only in host env vars (Render's sync: false blueprint entries). They are never committed — render.yaml contains no secrets, and a test asserts the repository stays that way.

Production webhook security

Register https://<your-service>.onrender.com/webhooks/paypal in the PayPal developer dashboard and set PAYPAL_WEBHOOK_ID to the id PayPal returns. Leave WEBHOOK_SHARED_SECRET unset: the dev HMAC strategy then fails closed (401), so only PayPal-signed deliveries — verified against PayPal's own API over the exact raw bytes — are ever accepted.
